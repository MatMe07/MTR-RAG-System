# Архитектурные решения (Architecture Decisions) — MTR-RAG

> Статус документа: **действующий** (2025-09-17)
> Связанные документы: `architecture_specification.md` (v2.0, контракт DTO).
> Здесь фиксируются **отклонения от плана v2.0**, принятые в ходе реализации,
> и их обоснование. Каждая запись: **контекст → решение → последствия**.

---

## AD-1: LangGraph вместо Planner/Executor/StateManager

**Контекст.** План v1.0/«Потом.md» предполагал классическую схему
Planner → Executor → StateManager с явным классом состояния. В период P1–P2
инструменты стали требовать графа согласованного вызова (C1+/C2, tool loops,
дважды проверяемые цепочки), а одиночный линейный Executor не давал:
- повторных итераций с LLM-уточнением без потери контекста;
- ветвления на `auto`/`agent`/`clarification` без распухания одного класса;
- stateless `/continue` (C2) без мгновенного восстановления состояния.

**Решение.** Вместо Planner/Executor/StateManager используется **LangGraph**
(`app/services/agent/executor.py`) с явными узлами `parse → classify → route →
verify → refine → format`, где состояние проходит через `AgentAnswer` на каждом
шаге. Вместо выделенного `StateManager` — **stateless** `/api/v1/agent/continue`
(+ `offer_endpoint`), состояние сериализуется в ответе, а не в памяти воркера.

**Последствия.**
- + Контекст не теряется между итерациями refine/verify (проблема «потерянных
  полей» v2.0 решена структурно).
- + C2-режим стал реализуемым без серверной сессии (горизонтальное масштабирование).
- − Появляется зависимость от LangGraph; узлы обязаны нести `Mode`/`AgentAnswer`
  в графе, иначе сложно отлаживать отклонения (это и есть предмет AD для
  `verification_verdict` и `mode_refined`).

**Отклонение от v2.0-плана:** заменён компонент «Planner/Executor/StateManager».

## AD-2: ToolDAL vs DataAccessLayer

**Контекст.** В ранней фазе данные читались только через `DataAccessLayer`
(единый `DAL`), что приводило к связыванию каталога, остатков и паспортов в
одном интерфейсе и к дублированию кэш-логики.

**Решение.** Разделение долей ответственности:
- **ToolDAL** (`ToolDAL`) — тонкий слой доступа к тулам агента
  (`search_ksm`, `search_catalog`, `get_unit_inventory`, `suggest_ksm_links`),
  без бизнес-логики для кандидатуры.
- **ToolDAL/DataAccessLayer** разведены: каталог и остатки — через
  `repository/providers/*`, вектор — через `VectorsProvider`.

**Последствия.**
- + Чёткие провайдеры (`passport_provider`, `catalog_provider`,
  `documents_provider`), независимо тестируемые.
- − Число файлов выросло; требуется документ `architecture_specification.md`,
  иначе поля «потеряются» (зафиксировано в v2.0).

## AD-3: Динамические правила из БД вместо хардкода

**Контекст.** Детерминированная логика (веса полей паспорта, пороги
валидации, `validation_constants`) была зашита в код.

**Решение.** Правила вынесены в БД-таблицу `validation_constants` (JSONB)
с фолбэком на дефолты кода (см. `_passport_weights()` в `passport_provider.py`).
Административные изменения правил не требуют редеплоя.

**Последствия.**
- + Правила обновляются без пересборки; `DEFAULT_PASSPORT_WEIGHTS` — только
  зеркало-дефолт.
- − Требуется синхронизация между дефолтами кода и значениями БД (формализовано
  в `schemas.py` → `validation_constants`).

## AD-4: BAAI/bge-m3 вместо all-MiniLM-L6-v2

**Контекст.** В v1.0 использовалась лёгкая встраивающая модель для кэш-поиска.
Для TЗ-метрики «Топ-3 ≥ 70%» линейная модель недостаточна по качеству
ранжирования технических параметров (DN/PN/angle/material).

**Решение.** Векторное ядро — **BAAI/bge-m3** (`embedding_provider.py`),
выбранная за сбалансированный трейд-офф качество/скорость/память и
поддержку многоязычия (RU техтексты).

**Последствия.**
- + Ранжирование технических кандидатов улучшено.
- − Дороже по памяти/токенам, чем l6; нагрузочные тесты (P3-25) должны
  подтвердить p95 < 500 мс.

## AD-5: Qdrant `documents` и векторные провайдеры

**Контекст.** П2-16 требовал векторный индекс паспортов (Qdrant `documents`).
В боевом репозитории коллекции `documents` исторически **не было** (только
`mtr_descriptions` в тестах), поэтому документные паспорта не попадали в
векторный поиск.

**Решение.** Создан `DocumentsProvider` (`documents_provider.py`) —
upsert страниц паспорта в Qdrant + `search`. Подключён в `DbRepository`
(`documents`-индекс) и в `passport_worker` (инкрементальный upsert после OCR,
не роняющий конвейер — guarded try/except).

**Последствия.**
- + Паспорта индексируются в `documents`.
- − Qdrant является внешней зависимостью; при недоступности — graceful
  degradation (warn, конвейер продолжает).

## AD-6: Mypy отсутствует в dev-зависимостях

**Контекст.** P3-24 (валидация схем) требует прогнать строгую типизацию.
`mypy` не установлен; в dev-зависимостях — только `ruff` + `pytest`.

**Решение.** Финальная валидация схем выполняется через **pydantic
(инстанс-валидацию)** — прогон полного набора тестов (555 passed / 12 skipped),
который конструирует каждый DTO с реальными данными. Отдельный статический
`mypy`-прогон не добавлен (чтобы не плодить конфигурацию).

**Последствия.**
- + Контракт подтверждён исполняемыми тестами, а не декларативной аннотацией.
- − Нет статической проверки типов вне runtime; компенсируется `mypy`-рулами
  при необходимости (см. AD-7).

## AD-7: Инструменты и проверки схем

**Контекст.** Для диаграммы «контракт DTO» важна согласованность полей
`AgentAnswer`/`ParsedQuery`/`ItemCard` с `schemas.py`.

**Решение.** Живой источник истины — `app/schemas.py`; `docs/architecture_specification.md`
генерируется/обновляется при изменении схем, с проверкой неиспользуемых
полей (скрипт `validate_schemas_doc` / отчёт одним прогоном в таблице раздела 4).

**Последствия.**
- + Документ не расходится с кодом.
- − Требует регенерации при каждом поле; закреплено как конвейер P3.
