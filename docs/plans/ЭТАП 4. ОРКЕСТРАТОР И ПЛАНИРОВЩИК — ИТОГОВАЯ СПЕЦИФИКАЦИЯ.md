## ЦЕЛЬ ЭТАПА 4

Создать ядро агента — оркестратор, который:
- Принимает структурированный запрос (ParsedRequest из Этапа 1).
- Выполняет запрос в одном из двух независимых режимов (выбор режима — за пользователем).
- Управляет состоянием выполнения, обрабатывает ошибки, формирует итоговый контекст.
- Передаёт контекст в Этап 5 для генерации финального ответа.

## 4A. ОБЩАЯ АРХИТЕКТУРА ОРКЕСТРАТОРА

```
Пользовательский запрос
        ↓
   [Выбор режима]  ←─── переключатель в UI
        ↓
┌───────────────────────────────┐
│  Режим 1: Детерминированный   │   ←─── основной, по умолчанию
│  (быстрый, предсказуемый)     │
└───────────────────────────────┘
        ↓
┌───────────────────────────────┐
│  Режим 2: LLM-управляемый     │   ←─── экспериментальный, гибкий
│  (медленнее, покрывает больше)│
└───────────────────────────────┘
        ↓
   AgentContext
        ↓
   Этап 5: Формирование ответа
```

Ключевое правило: режимы не пересекаются. Код, логика и конфигурация каждого режима изолированы.

## 4B. РЕЖИМ 1: ДЕТЕРМИНИРОВАННЫЙ (ОСНОВНОЙ)

### 4B.1 Компоненты

#### Planner (планировщик)

Ответственность: построение фиксированного плана выполнения на основе интентов.

Вход: List[Intent] — атомарные интенты из Этапа 1.
Выход: ExecutionPlan — упорядоченный список шагов с зависимостями.

Логика:

1. Для каждого интента определить список инструментов (из карты intent → tools, Этап 3).
2. Построить граф зависимостей между инструментами (на основе INTENT_DEPENDENCIES).
3. Упорядочить инструменты в топологическом порядке.
4. Сгруппировать инструменты, которые могут выполняться параллельно.
5. Сформировать ExecutionPlan.

Структура ExecutionPlan:

```
ExecutionPlan:
  - steps: List[ExecutionStep]
  - parallel_groups: List[List[ExecutionStep]]
  - estimated_duration_ms: int
```

#### Executor (исполнитель)

Ответственность: выполнение плана.

Вход: ExecutionPlan.
Выход: ExecutionContext.

Логика:

- Для каждой параллельной группы — запустить инструменты через asyncio.gather.
- Для последовательных шагов — выполнять по порядку.
- После каждого шага сохранять результат в ExecutionContext.
- При ошибке — передать управление ErrorHandler.

#### StateManager (менеджер состояния)

Хранит:

- completed_tools: List[str]
- results: Dict[str, ToolResult]
- errors: Dict[str, ToolError]
- retry_counts: Dict[str, int]

#### ErrorHandler (обработчик ошибок)

Логика:

| Тип ошибки | Действие |
|---|---|
| INVALID_PARAMS | Остановка, запрос уточнения у пользователя |
| NOT_FOUND | Пропуск (если инструмент не обязательный) |
| BATCH_TOO_LARGE | Повтор с уменьшенным размером батча |
| DAL_ERROR / TIMEOUT | Retry до 3 раз с экспоненциальной задержкой |
| UNKNOWN | Остановка, логирование |

Обязательные инструменты: search_catalog, get_component, check_stock — при их ошибке выполнение останавливается.
Необязательные: search_norms, get_component_history — при ошибке пропускаются.

### 4B.2 Этапы выполнения

```
1. Получить ParsedRequest (intents, params, request_id).
2. Planner.build_plan(intents).
3. Если план пуст → вернуть ошибку "Нет инструментов для выполнения".
4. Executor.execute(plan):
   a. Инициализировать StateManager.
   b. Для каждой параллельной группы:
      - Запустить инструменты.
      - Обработать ошибки через ErrorHandler.
      - Сохранить результаты.
   c. Для последовательных шагов — аналогично.
   d. При ошибке с кодом "STOP" — прервать выполнение.
5. ContextBuilder.build(execution_context).
6. Вернуть AgentContext.
```

### 4B.3 Время выполнения

Целевое: < 10 секунд.

Максимальное: 30 секунд (согласно ТЗ, раздел 17).

## 4C. РЕЖИМ 2: LLM-УПРАВЛЯЕМЫЙ (ЭКСПЕРИМЕНТАЛЬНЫЙ)

### 4C.1 Назначение

Обработка запросов, которые:

- Не покрываются картой интентов (нетипичные комбинации).
- Требуют нестандартной последовательности действий.
- Пользователь явно выбрал этот режим в интерфейсе.

### 4C.2 Компоненты

#### LLMAgent (главный класс)

Ответственность: управление циклом LLM-вызовов и выполнение решений.

Вход:
- user_query: str (оригинальный текст).
- extracted_params: dict (из Этапа 1).
- intents: List[Intent] (для контекста, но не для планирования).

Выход: AgentContext.

Цикл:

```
1. Получить список всех доступных инструментов с их описаниями.
2. Сформировать начальный промпт (инструкция + описание инструментов + запрос).
3. Цикл (макс. 10 итераций):
   a. Отправить промпт в LLM.
   b. Получить ответ в формате JSON:
      - {"action": "call_tool", "tool_name": "...", "input": {...}}
      - {"action": "ask_user", "question": "..."}
      - {"action": "finish", "final_answer": "..."}
   c. Если "call_tool" — выполнить инструмент, получить результат.
   d. Добавить результат в промпт (история).
   e. Если "ask_user" — приостановить выполнение, передать вопрос в UI, дождаться ответа.
   f. Если "finish" — завершить цикл.
4. Если лимит итераций исчерпан — принудительное завершение.
5. Собрать все результаты в AgentContext.
```

#### ToolRegistry (реестр инструментов)

Содержит для каждого инструмента:
- name
- description
- input_schema
- output_schema
- execute (функция-обёртка)

Эти данные передаются LLM в промпте для выбора действий.

#### LLMResponseParser (парсер ответа)

Проверяет:

- Валидность JSON.
- Наличие поля action.

Если action == "call_tool":

- Существует ли tool_name в реестре.
- Валидны ли input по input_schema.

Если action == "ask_user":

- Наличие поля question.

Если action == "finish":

- Наличие поля final_answer.

При невалидном ответе — повторный запрос к LLM с уточнением.

#### LLMExecutor (исполнитель действий)

Обрабатывает:

- call_tool — вызывает инструмент через ToolRegistry.execute().
- ask_user — возвращает управление в UI, ожидает ответ, возобновляет цикл.
- finish — завершает выполнение.

### 4C.3 Ограничения (защита)

```
- Максимальное число итераций: 10.
- Максимальное время выполнения: 60 секунд.
- Запрет на повторный вызов одного инструмента с одинаковыми параметрами более 2 раз подряд.
- При превышении любого ограничения — принудительное завершение с сообщением:
  "Достигнут лимит попыток. Попробуйте детерминированный режим или уточните запрос."
```

### 4C.4 Логирование (для аудита)

Для каждого шага логируется:

- Номер итерации.
- Промпт (текст, отправленный в LLM).
- Ответ LLM (включая выбранное действие).
- Результат выполнения инструмента (или вопрос пользователю).
- Время выполнения шага.

Хранилище: PostgreSQL, таблица llm_agent_logs.

### 4C.5 Критерии остановки

LLM должна завершить работу, если:

- Найдена деталь с match_score >= 95% (статус "Соответствует").
- Найдено 3+ кандидата с match_score >= 80%.
- Выполнены все инструменты, которые LLM считает необходимыми.
- LLM решила, что данных недостаточно, и запросила уточнение (переходит в ask_user).

## 4D. ИНТЕГРАЦИЯ ДВУХ РЕЖИМОВ В ОРКЕСТРАТОР

### 4D.1 Выбор режима

```
mode = request.mode  # "deterministic" | "llm"
```

По умолчанию: deterministic.

Переключение: через UI (переключатель или выбор в настройках запроса).

### 4D.2 Логика выбора в оркестраторе

```
if mode == "deterministic":
    context = DeterministicOrchestrator.execute(request)
elif mode == "llm":
    context = LLMOrchestrator.execute(request)
else:
    error = "Неизвестный режим"
```

Важно: режимы не вызывают друг друга. Каждый работает автономно.

### 4D.3 Рекомендация пользователю (опционально)

Если детерминированный режим вернул:

- Статус UNCLEAR — UI предлагает: "Не удалось однозначно определить запрос. Попробовать LLM-режим?"
- Статус REQUIRES_EXPERT — аналогично.

Предложение отображается в UI, но не приводит к автоматическому переключению.

## 4E. ОБЩИЙ ПОТОК ВЫПОЛНЕНИЯ (ОБА РЕЖИМА)

```
1. Получить ParsedRequest (intents, params, request_id, mode).
2. Если mode == "deterministic":
   a. Planner.build_plan(intents) → план.
   b. Executor.execute(план) → контекст.
   c. ErrorHandler при ошибках.
3. Если mode == "llm":
   a. LLMAgent.run(user_query, params, intents) → контекст.
   b. LLMExecutor обрабатывает действия.
   c. Ограничения (итерации, время) контролируются.
4. ContextBuilder.build(execution_context) → AgentContext.
5. Вернуть AgentContext в Этап 5.
```

## 4F. СТРУКТУРА AGENTCONTEXT

```
AgentContext:
  - request_id: UUID
  - mode: str                    # "deterministic" | "llm"
  - intents: List[Intent]
  - params: dict
  - tool_results: Dict[str, ToolResult]
  - errors: List[ToolError]
  - warnings: List[str]
  - execution_time_ms: int
  - llm_iterations: int (только для llm-режима)
  - final_status: str             # SUCCESS, PARTIAL, UNCLEAR, REQUIRES_EXPERT
```

# КРИТЕРИИ ГОТОВНОСТИ

- Детерминированный режим работает по спецификации (Planner, Executor, ErrorHandler).
- LLM-управляемый режим реализован как отдельный компонент.
- LLM получает список инструментов с их описаниями.
- LLM умеет возвращать три типа действий: call_tool, ask_user, finish.
- Исполнитель корректно обрабатывает все три типа действий.
- Защитные ограничения реализованы (10 итераций, 60 секунд, защита от повторов).
- Логирование всех шагов LLM-режима реализовано.
- В UI добавлен переключатель режимов.
- При статусах UNCLEAR/REQUIRES_EXPERT в детерминированном режиме пользователю предлагается переключиться на LLM-режим.
- Интеграционные тесты проверяют оба режима на наборе из 20 запросов.
- Время выполнения: детерминированный < 10 сек, LLM < 60 сек.
