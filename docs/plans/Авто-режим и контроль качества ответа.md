# План: Авто-режим (гибрид deterministic + LLM) и контроль качества ответа

**Статус:** ЧЕРНОВИК (план, не реализация)
**Автор:** Анализ выполнения запросов MTR-RAG-System
**Дата:** 2026-08-31
**Область:** `backend/app/services/agent/` (executor, llm, answer, parsing, tools)

---

## 1. Контекст и мотивация

### 1.1. Наблюдённые дефекты при детерминированном исполнении

При разборе реальных инвентарных запросов выявлены случаи, когда **результат детерминированного пайплайна технически корректен, но не отвечает на запрос пользователя**:

| Запрос | Что ожидалось | Что вернул deterministic-режим |
|--------|---------------|--------------------------------|
| «Проверь, хватает ли труб, отводов, ... **по две штуки**» | Verdict «не хватает 2 шт. задвижек», «хватает труб» + сравнение спроса и остатка | Просто список позиций со срочностью; **потребность «2 шт.» не учтена**, deficit не вычислен |
| «…которых сейчас нет на складе, расставь по срочности» | Только отсутствующие позиции + ранжирование | (исправлено) catalog-кандидаты с остатком засоряли ответ |

Детерминированные правила не всегда покрывают **семантический замысел** запроса (намерение «проверь, хватает ли», количественные требования «по N штук», скрытые связи между типами деталей). Именно поэтому существует LLM-режим — он умеет интерпретировать ответ в терминах запроса. Но полный LLM-режим дорог и недетерминирован для простых запросов.

### 1.2. Цель

Ввести **третий режим «Авто» (auto)**, который:
1. Сначала выполняет быстрый **детерминированный** проход (дёшево, воспроизводимо).
2. Применяет **авторевью-проверку соответствия ответа запросу** (лексические/структурные эвристики).
3. Если проверка показала **низкое соответствие** или **высокую сложность запроса** — **эскалирует на LLM**, который либо до-оформляет ответ, либо перезапускает цикл с учётом семантики.

Также добавить **обязательный слой контроля качества** (quality gate) для deterministic-режима, чтобы он сам определял момент, когда детерминированный ответ «не подходит под запрос» и предлагал/выполнял LLM-доработку.

## 2. Дизайн решения

### 2.1. Концептуальная схема

```
Пользовательский запрос
        │
        ▼
┌─────────────────────┐
│  MODE ROUTER        │  (новый, для mode="auto")
│  выбирает маршрут   │
└─────────────────────┘
   │ deterministic │ llm
   ▼               ▼
┌──────────────┐  ┌──────────────────┐
│ Determ. pipe │  │ Direct LLM agent │  (существующий mode="llm")
│ (граф)       │  └──────────────────┘
└──────┬───────┘
       ▼
┌──────────────────────────────┐
│  QUALITY GATE / VERIFIER     │  (новый; для auto — всегда; для deterministic — по флагу)
│  1. Проверка соответствия    │
│     запросу (эвристики)      │
│  2. Возврат: PASS / REVIEW   │
│  3. При REVIEW → вызов LLM:  │
│     а) дооформить ответ      │
│     б) или перезапустить     │
└──────────────┬───────────────┘
               ▼
       Итоговый AgentAnswer
```

### 2.2. Три режима

| mode | Маршрут | Когда применять |
|------|---------|-----------------|
| `deterministic` | граф → ответ (с авторевью по желанию) | Простые, типовые запросы; демо; тесты |
| `llm` | напрямую LLMAgent (call_tool/ask_user/finish) | Сложная семантика, требующая интерпретации |
| `auto` (**новый**) | deterministic граф → quality gate → при необходимости LLM | Универсальный выбор по умолчанию для UI |

### 2.3. Принцип работы mode="auto"

1. **Шаг A — детерминированный проход** (как сейчас): `graph.invoke(...)`.
2. **Шаг B — качественный затвор (quality gate)** `_auto_verify(parsed, answer)`:
   - Возвращает `PASS` (ответ соответствует запросу, можно отдавать) или `REVIEW` (нужна доработка LLM).
   - Критерии REVIEW смотри в §3.
3. **Шаг C — обработка REVIEW:**
   - **Вариант С1 (рекомендуемый): LLM-дооформление ответа** — передать LLM-агенту уже собранный structured-ответ + исходный запрос + недостатки из затвора; LLM правит `answer_text`/`explanation`/`reasoning`, не перезапуская весь цикл. Дёшево (1 вызов), сохраняет детерминированные данные.
   - **Вариант С2: полный перезапуск LLMAgent** `_execute_llm(...)` — если запрос настолько сложный, что дооформление бессмысленно (например, требуется интерпретация количественных требований).
   - Решение С1 vs С2 — по эвристике (тип несоответствия, см. §4).

## 3. Качественный затвор (quality gate / verifier)

Новый модуль: `backend/app/services/agent/verify/verifier.py` (или `answer/verifier.py`).

### 3.1. Интерфейс

```python
VerificationResult:
    verdict: str            # "pass" | "review"
    reasons: List[str]      # человекочитаемые причины (4C-лог)
    gaps: List[Dict]        # структурированные недостатки
        # {type: "intent_mismatch"|"quantity_unmet"|"scope_mismatch"|"parameter_miss"|...,
        #  detail: "...", severity: "low"|"med"|"high"}

def verify_answer(parsed: ParsedQuery, answer: AgentAnswer) -> VerificationResult
```

### 3.2. Эвристики проверки (детерминированные)

Проверки накладываются на **parsed + answer.components + answer.warnings + answer.recommendations**.

| # | type | Условие REVIEW | Пример срабатывания |
|---|------|----------------|---------------------|
| 1 | `intent_mismatch` | `parsed.plotting/necessary entity` не покрыто ответом. Высокий severity, если в `parsed.intents` есть `CHECK_SUFFICIENCY`/`PLAN_REPAIR`, а в answer нет verdict-поля. | «проверь, хватает ли по 2 шт.» — ответ без verdict |
| 2 | `quantity_unmet` | В запросе распознано количественное требование (units_count / «по N штук»), но ответ не сравнивает спрос и остаток по типам. | запрос выше |
| 3 | `scope_mismatch` | Все компоненты ответа — одного типа (например, только «труба»), хотя запрошено 6 типов. | трубы забивают топ, а нужны и отвод/задвижка |
| 4 | `zero_stock_missing` | Для интента `LIST_OUT_OF_STOCK` в components есть позиции с quantity>0 с match_score (каталог), т.е. фильтр «нет на складе» не применён. | старый баг с трубами |
| 5 | `parameter_miss` | `parsed.ambiguities` непуст и ответ не предлагает уточнение (нет clarification route). | «Не удалось определить тип детали» |
| 6 | `empty_or_expert_silent` | `status == require_expert` и `explanation` пуст и `recommendations` содержат только дефолт «попробовать LLM». | пустой шумный expert-ответ |

### 3.3. Порог решения

- `max severity == high` → `REVIEW` и **С2 (полный LLM-перезапуск)**.
- `medium`/несколько `low` → `REVIEW` и **С1 (LLM-дооформление)**.
- иначе → `PASS`.

## 4. Решение С1 vs С2 (маршрут эскалации)

Сконцентрировать в отдельной функции `_should_full_llm(gaps)` в verifier-модуле:

```python
FULL_LLM_TYPES = {"intent_mismatch", "quantity_unmet", "scope_mismatch"}
```

- Если среди `gaps` есть тип из `FULL_LLM_TYPES` с `severity == high` → **полный LLMAgent** (С2).
- Иначе → **дооформление** (С1).

## 5. Реализация дооформления (С1) — LLM-редактор ответа

Новый модуль `backend/app/services/agent/llm/refine.py`:

```python
def refine_answer(
    llm: LLMClient,
    query: str,
    answer: AgentAnswer,
    gaps: List[Dict],
) -> AgentAnswer:
    """Одним LLM-вызовом улучшает текстовую часть ответа и explanation,
    сохраняя структуру components/sources/warnings (детерминированные данные).
    """
```

### 5.1. Промпт дооформления

Передаётся:
- исходный запрос пользователя
- структурированный детерминированный ответ (components, статусы, рекомендации, warnings)
- список недостатков (`gaps`) — что именно не отвечает запросу

LLM возвращает JSON:
```json
{
  "answer_text": "исправленный пользовательский текст ответа",
  "explanation": "краткое обоснование",
  "extra_recommendations": ["..."],
  "confidence_gate": "pass" | "still_unclear"
}
```
Если `confidence_gate=="still_unclear"` → вернуть answer с флагом `llm_refine_failed=True`, статус остаётся `требует экспертной проверки`, но `answer_text` уже формально отвечает на запрос (verdict-строки).

### 5.2. Сохранение целостности

- `refine_answer` **не трогает** `components`, `sources`, `warnings` — они остаются детерминированными (проверяемы).
- Изменяет только `answer_text`, `explanation`, добавляет `recommendations`.
- Добавляет метку `mode_refined="auto_llm_refine"` и `verification=VerificationResult`.

## 7. Связь с будущей «проверкой достаточности» (CHECK_SUFFICIENCY)

Запрос «хватает ли ... по N штук» требует отдельного шага в детерминированном графе, **до** затвора:

1. **Парсер** — распознавать «по N штук» → `parsed.units_count = N` и интент `CHECK_SUFFICIENCY` (`parsing/hybrid_parser.py`, `intent/matrix.py`, `intent/detect.py`).
2. **Инструмент** `sufficiency_check` (в `tools/analytic_tools.py`) — агрегировать суммарный остаток **по типу детали** и сравнить c `N`:
   - `sum_stock(type) >= N` → статус «хватает»
   - иначе → «не хватает, дефицит = N - sum_stock», срочность из существующей urgency-модели.
3. **Затвор** проверяет, что для `CHECK_SUFFICIENCY` в ответе есть verdict-строка по каждому запрошенному типу (**эвристика `quantity_unmet` / `scope_mismatch`)** → иначе REVIEW и LLM-эскалация.

Этот шаг — отдельный под-этап (см. `docs/plans/Проверка достаточности.md` при желании), но Авто-режим страхует и когда он ещё не реализован: затвор заметит пропуск потребности и включит LLM.

## 9. Тестирование

### 9.1. Юнит-тесты
- `test_verifier.py` — каждая эвристика (§3.2): подобрать crafted `parsed+answer`, ожидать `PASS`/`REVIEW` с нужным `gap.type`.
- `test_policy.py` — пороги: severity и `should_full_llm`.
- `test_refine.py` — `refine_answer` сохраняет components, меняет только текст; мок LLM.

### 9.2. Интеграционные (детерминированный + auto)
- Наблюдаемые кейсы:
  - H2S «нет на складе / срочность» → `PASS` (после исправления).
  - H2S «по две штуки / хватает ли» → `REVIEW` (гэп `quantity_unmet`), при авто → LLM дооформляет verdict.
- Проверить: answer сохраняет components, но `answer_text` содержит «не хватает: задвижки 2 шт.».

### 9.3. Метрики (evaluation)
- `data/evaluation/40_questions.jsonl`-набор прогнать в режиме auto.
- Сравнить средний `match` + скорость + долю LLM-эскалаций по типам запросов.
- Цель: авто не должен эскалировать типовые запросы (труба по коду, простой каталог), а эскалировать — inventory с количеством/суффицитом.

## 10. Критерии готовности (Definition of Done)

1. `mode="auto"` работает в `app_console` и frontend-UI.
2. `verify_answer` покрывает минимум эвристики §3.2 (все 6).
3. Запрос «хватает ли ... по 2 шт.» в auto-режиме возвращает `PASS`-или-`REVIEW`+LLM-verdict, в котором явно сказано, каких типов не хватает.
4. Deterministic-режим по-прежнему отдаёт прежние ответы (без поломки 261 теста).
5. Есть юнит-тесты verifier/policy/refine и интеграционные на кейсах H2S.
6. Логирование: executer пишет `verdict=pass|review reasons=[...] escalation=C1|C2`.
