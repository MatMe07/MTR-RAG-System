## ЦЕЛЬ ЭТАПА 5

Создать модуль, который:

- Принимает AgentContext (результаты выполнения инструментов, ошибки, предупреждения).
- Генерирует структурированный JSON-ответ по спецификации ТЗ (раздел 11.2).
- Добавляет человекочитаемые объяснения (шаблонные или с LLM).
- Включает ссылки на источники (паспорта, Excel, ЛНД с указанием разделов).
- Определяет статус ответа с учётом критических параметров и предупреждений.
- Передаёт идентификатор запроса эксперту при статусе REQUIRES_EXPERT.

## 5A. КОМПОНЕНТЫ МОДУЛЯ ОТВЕТА

### 5A.1 ResponseBuilder (базовый сборщик)

Ответственность: формирование структуры ответа (каркаса) на основе AgentContext.

Вход: AgentContext.
Выход: RawResponse.

Логика:

```
1. Извлечь результаты выполнения инструментов из context.tool_results.
2. Определить статус ответа (через StatusDeterminator).
3. Собрать найденные детали (из search_catalog, get_component).
4. Собрать информацию о складе (из check_stock).
5. Собрать результаты совместимости (из check_compatibility).
6. Собрать соседей (из get_neighbors).
7. Собрать источники (паспорта, Excel, ЛНД) через SourceFormatter.
8. Собрать предупреждения и ошибки.
9. Сформировать RawResponse.
```

Структура RawResponse:

```
RawResponse:
  - status: str
  - query: str
  - mode: str
  - critical_params: List[str]           # параметры, помеченные как блокеры
  - candidates: List[dict]
  - stock_info: Dict[str, dict]
  - compatibility_info: Dict[str, dict]
  - neighbors_info: Dict[str, list]
  - warnings: List[str]
  - errors: List[dict]
  - sources: List[SourceRef]
  - matched_params: List[str]
  - mismatched_params: List[str]
  - missing_params: List[str]
  - explanation_data: dict
```

### 5A.2 StatusDeterminator (определитель статуса)

Ответственность: финальное определение статуса ответа с учётом критических параметров и предупреждений.

Логика (последовательность проверок):

```
1. Если есть ошибки с кодом "STOP" → статус REQUIRES_EXPERT.
2. Если есть ошибки INVALID_PARAMS → статус UNCLEAR.
3. Если найден кандидат с match_score >= 95% → предварительный статус SUCCESS.
4. Если есть warnings (любые, кроме "необязательных"):
   - Если warning касается критического параметра → статус REQUIRES_EXPERT.
   - Если warning не критический → понизить статус до PARTIAL.
5. Если найдены кандидаты с match_score >= 70% → статус PARTIAL.
6. Если найдены кандидаты с match_score < 70% → статус PARTIAL (с предупреждением).
7. Если нет кандидатов → статус NOT_FOUND.
8. Если запрос не распознан → статус UNCLEAR.
```

Маппинг статусов в ТЗ (раздел 9):

| Статус системы | Статус в ТЗ |
|---|---|
| SUCCESS | Соответствует |
| PARTIAL (≥70%) | Потенциальный аналог |
| PARTIAL (<70%) | Не соответствует |
| NOT_FOUND | Нет данных |
| UNCLEAR | Требует проверки |
| REQUIRES_EXPERT | Требует экспертной проверки |

### 5A.3 ExplanationGenerator (генератор объяснений)

Ответственность: создание человекочитаемого текстового объяснения на основе RawResponse.

Режимы работы:

| Режим | Когда используется | Что делает |
|---|---|---|
| Шаблонный (без LLM) | Для штатных ответов, статус SUCCESS или PARTIAL | Генерирует объяснение по жёсткому шаблону. |
| LLM-генеративный | Для статусов UNCLEAR, REQUIRES_EXPERT или при явном запросе "объясни" | Использует LLM для адаптивного текста. |

Шаблонный режим (без LLM):

```
"Найдено {count} кандидатов.

Не совпавшие параметры: {mismatched_params}. 
Недостающие параметры: {missing_params}. 
Рекомендация: {recommendation}."
```

### 5A.4 SourceFormatter (форматировщик источников)

Ответственность: формирование ссылок на источники в едином формате.

Вход: список источников из RawResponse.
Выход: структурированный список SourceRef.

```
SourceRef:
  - type: str                  # passport, excel, norm, catalog
  - document_id: str (опционально)
  - page: int (опционально)
  - row: int (опционально)
  - section: str (опционально)      # общий раздел документа
  - lnd_section: str (опционально)  # раздел ЛНД (например, "5.3")
  - description: str                # "Паспорт задвижки, стр. 2"
  - url: str (опционально)
```

Логика:

1. Из tool_results извлекаются все ссылки на источники.
2. Группируются по типу.
3. Приводятся к единому формату.
4. Для ЛНД-документов заполняется lnd_section.

## 5C. ИНТЕГРАЦИЯ С ЭТАПОМ 4

```
Этап 4 → AgentContext → Этап 5 → JSON-ответ → UI
```

| Передаваемые данные | Откуда |
|---|---|
| mode | Из запроса пользователя |
| query | Оригинальный текст запроса |
| critical_params | Из Этапа 1 (BLOCKER_FIELDS) |
| tool_results | Из Этапа 4 (исполненные инструменты) |
| errors, warnings | Из Этапа 4 (StateManager / ErrorHandler) |
| request_id | Из запроса (генерируется в Этапе 1) |

## 5D. ТЕСТИРОВАНИЕ

### 5D.1 Unit-тесты

| Тест | Что проверяет |
|---|---|
| test_response_builder_success | Формирование ответа при статусе SUCCESS |
| test_response_builder_partial | Формирование ответа при статусе PARTIAL |
| test_response_builder_unclear | Формирование ответа при статусе UNCLEAR |
| test_status_determinator_warnings | Понижение статуса при наличии warnings |

| test_source_formatter_lnd | Форматирование источников с разделом ЛНД |
| test_explanation_generator_template | Генерация шаблонного объяснения |
| test_explanation_generator_llm | Генерация объяснения через LLM |

### 5D.2 Интеграционные тесты

| Сценарий | Проверяет |
|---|---|
| Полный цикл: запрос → парсинг → оркестратор → ответ | Корректность финального JSON |
| Статус SUCCESS | Наличие кандидатов, отсутствие ошибок |
| Статус UNCLEAR | Наличие рекомендаций по уточнению |
| Статус REQUIRES_EXPERT | Флаг requires_expert = true, наличие expert_review_id |
| Наличие источников с ЛНД-разделами | Поле lnd_section заполнено |

### 5D.3 Визуальная проверка

- UI отображает JSON-ответ в читаемом виде (таблица кандидатов, предупреждения, рекомендации).
- Ссылки на источники кликабельны (ведут к паспорту/Excel-строке/разделу ЛНД).
- Для статуса REQUIRES_EXPERT отображается expert_review_id.

## КРИТЕРИИ ГОТОВНОСТИ

- ResponseBuilder формирует RawResponse на основе AgentContext.
- StatusDeterminator корректно определяет статус с учётом критических параметров и warnings.
- ExplanationGenerator работает в двух режимах (шаблонный и LLM).
- В LLM-режим передаётся список critical_params.
- SourceFormatter приводит все источники к единому формату, включая lnd_section.
- Итоговый JSON-ответ соответствует спецификации ТЗ (раздел 11.2).
- Для статусов UNCLEAR и REQUIRES_EXPERT формируются понятные рекомендации.
- При статусе REQUIRES_EXPERT в ответе присутствует expert_review_id.
- Все тесты пройдены.
- UI корректно отображает все поля ответа.
