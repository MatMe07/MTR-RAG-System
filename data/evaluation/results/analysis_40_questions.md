# Анализ результатов 40ых вопросов — MTR-RAG-System

**Дата:** 2026-09-02
**Режим запуска:** deterministic (offline_rules)
**LLM:** недоступен (все 40 запросов)
**Каталог:** 1000 карточек (синтетический)

---

## КРИТИЧЕСКИЕ СИСТЕМНЫЕ ПРОБЛЕМЫ

### 1. LLM всегда недоступен — все 40 ответов без смыслового ядра

Все 40 результатов содержат:
```
explanation='{"response": "LLM недоступен"}'
mode='offline_rules'
answer='Проверено 3 нормативов'
```

Система работает как чистый детерминированный конвейер без единого шага генерации текста. Ответы — это сырые структурированные данные (`AgentComponent(...)`), а не ответы на вопрос.

**Последствие:** пользователь получает массив объектов вместо развёрнутого текста. Ни один из 40 запросов не получил ответ в виде человеческого языка. Без LLM категорически невозможно:
- Объяснить параметры «простыми словами» (AQ021, AQ022, AQ025)
- Сформулировать план работ (AQ016, AQ017, AQ018, AQ030–AQ035)
- Сформулировать предупреждения (AQ001–AQ007)
- Показать анализ влияния текстом (AQ036–AQ038)

### 2. `completed=False` на всех 40 запросах

Граф **никогда не доходит до `answer_node`**. Состояние графа не обнуляется, `answer_node` не ставится как конечный узел. Все ответы строятся через `_build_answer_from_result` — fallback, а не через штатный пайплайн построения ответа.

Это означает, что условие выхода из графа (router → answer) не срабатывает ни разу за 40 запросов.

### 3. Все инструменты запускаются на каждый запрос (нет точечного вызова)

На **каждый** из 40 запросов запускаются `graph_search`, `catalog_search`, `stock_query`, `rules_engine`, `regulation_lookup`, а часто и `impact_analyzer`, `maintenance_planner` — даже когда запрос простой (AQ021, AQ022, AQ025 — справочные вопросы без контекста участка).

Это даёт:
- Шум в ответе (лишние компоненты из других участков)
- Потерю времени (запрос на объяснение термина запускает 5+ инструментов)
- Нерелевантные данные в components (WATER-001 в ответе на вопрос про H2S-участок)

### Inventory (AQ008–AQ015) — склад и запасы

**Это самая слабая категория (8 из 40 вопросов — 20%).**

| Вопрос | Статус | Проблема |
|--------|--------|----------|
| AQ008 | Критично | Запрос «нет на складе» → результат содержит позиции с `quantity=73`, `quantity=19` и т.д. **Фильтр нулевого остатка не работает** |
| AQ009 | Критично | Запрос «хватает ли по две штуки» → не показано сколько штук нужно vs сколько есть. `sufficiency_check` вернул `all_sufficient=False`, но в components это не отражено |
| AQ010 | Плохо | Вернул 12 отводов 90-426x10 без фильтрации по H2S-пригодности. Все показаны как `tz_status='соответствует'` |
| AQ011 | Критично | Запрос «10 самых важных» → вернул позиции с остатком 66–75 штук (переходы). Не показывает десятку, не ранжирует по срочности |
| AQ012 | Критично | Запрос «запас для 3 участков + страховой комплект» — не performing умножение на 3, не показывает дефицит по каждой позиции |
| AQ013 | Плохо | Запрос «найди дубли» → `duplicate_detector` вернул 40 компонентов **без группировки** по схожим параметрам |
| AQ014 | Критично | Запрос «остаток > 50, не установлены нигде» → вернул позиции с `quantity=13`, `quantity=49` (меньше 50). **Порог не фильтруется** |
| AQ015 | Критично | Запрос «остаток < 3» → вернул позиции с `quantity=26`, `quantity=19`, `quantity=11`. **Фильтр не работает** |

**Корневая причина:** `stock_query` и `inventory_calculator` **добавляют** данные в state, но **не фильтруют** их по пороговым значениям из вопроса. Фильтрация должна быть в answer_builder или в отдельном фильтре перед построением ответа.

## ТОП-5 КОРНЕВЫХ ПРОБЛЕМ (приоритет устранения)

### 1. Нет LLM → 40/40 ответов без текста
Система useless в текущем виде без LLM. Все категорийные ответы (планы, объяснения, предупреждения, анализы) требуют генерации текста.

**Решение:** наладить LLM-пайплайн (OpenRouter/DummyLLM) или реализовать шаблонные текстовые ответы для `offline_rules` режима.

### 2. `completed=False` на графе → answer_node не отрабатывает
Все 40 запросов завершаются через fallback `_build_answer_from_result`, а не через штатный `answer_node`. Условие выхода из графа (router → answer) не срабатывает.

**Решение:** проверить условие перехода `router()` → `answer` и убедиться, что граф завершается корректно.

### 3. Нет фильтрации по порогам из вопроса
Запросы «< 3 штук», «> 50 штук», «0 на складе» возвращают случайные значения. Фильтры пороговых значений не применяются.

**Решение:** добавить этап фильтрации после `stock_query`/`inventory_calculator`, который извлекает пороги из `parsed.technical_filters` и фильтрует `components`/`stock_rows`.

### 4. Нет actual reasoning в аналитических инструментах
`inventory_calculator`, `duplicate_detector`, `maintenance_planner` добавляют данные, но не обрабатывают их — не группируют, не ранжируют, не фильтруют, не считают дефицит.

**Решение:** расширить инструменты: `inventory_calculator` должен считать дефицит и «нужно vs есть», `duplicate_detector` — группировать, `maintenance_planner` — формировать текстовый план.

### 5. Нет context-aware tool selection
Справочный запрос (AQ021–AQ025) запускает `impact_analyzer` + `maintenance_planner` + `graph_search`. Intent resolver не блокирует лишние вызовы.

**Решение:** в `router()` добавить проверку `intent` и пропускать узлы, которые не релевантны (не вызывать `impact` для `equipment_guidance`, не вызывать `maintenance` для `inventory`).
